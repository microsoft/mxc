# MXC Versioning

> Five-slide developer presentation
>
> September 22, 2026

---

## Slide 1 — Why MXC Configuration Is Versioned

**A config version is a compatibility promise, not a feature flag.**

- Configs are produced by humans, SDKs, automation, templates, LLMs, and
  agents.
- Configs are stored, copied, generated, and executed by different releases.
- Every request declares an **exact registered version**, such as
  `0.9.0-alpha`.
- Published contracts are immutable: an existing config must continue to mean
  the same thing.
- Development contracts can evolve until they are published.
- Closed contracts reject unknown or misplaced fields instead of silently
  ignoring them.

**Why closed schemas matter:** a plausible-looking unsupported security policy
must fail explicitly, especially when a config was generated by an LLM.

**Key takeaway:** Adding a field to the runtime model does not automatically
make it legal in every contract version.

## Slide 2 — The Version-Aware Request Pipeline

```text
JSON configuration
    ↓ exact version dispatch
Version-specific closed request type
    ↓ version-specific adapter
CommonRequestIR
    ↓ shared normalization
ExecutionRequest
    ↓
Selected backend
```

- Production does **not** deserialize through one rolling superset request
  type.
- Each version owns its accepted JSON shape, aliases, defaults, and request
  roots.
- Request roots are phase-specific: one-shot, provision, start, exec, stop,
  and deprovision.
- Adapters remove wire-version differences before shared runtime logic begins.
- Backends consume `ExecutionRequest`; they do not need to understand
  historical schemas.

**Key takeaway:** Version-specific behavior belongs at the contract boundary,
not scattered throughout backend implementations.

## Slide 3 — What Developers Must Do

When adding a configuration feature:

1. Decide **which contract first exposes the feature**.
2. Add it to that version's exact Rust contract.
3. Add or update the contract-to-runtime adapter.
4. Register any new request root in `ContractDescriptor`.
5. Add valid and invalid fixtures for every applicable root.
6. Regenerate the schema and TypeScript wire oracle.
7. Update public SDK types, runtime validation, and documentation as
   applicable.

**Important rules**

- Never modify a schema in `schemas/stable/`.
- Never hand-edit generated schemas or generated TypeScript wire files.
- Do not add new fields to older published request types.
- Preserve optional-field presence through adapters.
- Let backend validation enforce backend-specific semantics.
- Generated TypeScript wire files are drift oracles, not the public SDK API.

## Slide 4 — The v1 Compatibility Model

**High-level SDK APIs target a major version line.**

- Consumers should be able to upgrade between compatible SDK minor versions
  without changing existing application code.
- Consumers only need code changes when they choose to use a newly added
  minor-version feature.
- Moving to a new major version may require source changes.
- Raw configuration documents still declare an exact contract version.
- The SDK selects an appropriate exact contract within its supported major
  line.
- v1 networking is directional-only; legacy networking fields do not return.

```text
SDK 1.0 application
    → upgrades to SDK 1.1
    → existing code continues to work
    → new 1.1 fields are available when explicitly adopted
```

**Current versus planned**

- Exact registered contracts and version-specific adapters exist today.
- Major-line SDK compatibility is the planned v1 SDK behavior.

**Key takeaway:** Exact wire contracts give the native boundary strictness;
major-line SDK APIs give consumers compatibility.

## Slide 5 — The v1 Transition and Its Safety Gates

### Contract lineage

- **v1.0 starts from published v0.9**, not from the mutable v0.10 development
  contract.
- Every v0.10-only feature moves to **v1.1 development**:
  - abstract `vm` containment;
  - Windows Sandbox one-shot and provision surfaces;
  - Windows Sandbox timeout and daemon-pipe fields;
  - MicroVM;
  - Hyperlight; and
  - the top-level test feature.
- WSLC, IsolationSession, directional networking, and common state-aware
  phases are already part of the v0.9 baseline.

### CI protects the promise

- Regenerated schemas and TypeScript oracles must match committed artifacts.
- Rust fixtures verify exact Serde acceptance and rejection.
- AJV verifies the generated schema against the same valid and invalid
  fixtures.
- The repository config corpus is validated against the exact schema named by
  each config.
- Schema-version constants are checked across Rust, Node, and .NET.

**Question to ask before opening a PR:**

> Which exact contract owns this field, and what compatibility promise does
> adding it create?
