# MXC Versioning

> Five-slide developer presentation
>
> September 22, 2026

---

## Slide 1 — Why MXC Configuration Is Versioned

**A config version identifies a precise compatibility contract.**

- Configs are produced by humans, SDKs, automation, templates, LLMs, and
  agents.
- Configs are stored, copied, generated, and executed by different releases.
- Every request declares an **exact registered version**, such as
  `0.9.0-alpha`.
- Published contracts are immutable: an existing config must continue to mean
  the same thing.
- Development contracts can evolve until they are published.
- Closed contracts define every accepted field, location, type, and request
  root.
- Validation gives config authors immediate feedback when a request falls
  outside the selected contract.

**Why closed schemas matter:** every accepted security policy has an explicit,
machine-readable meaning, including policies generated by LLMs and agents.

**Key takeaway:** The selected contract determines the exact configuration
language understood by MXC.

## Slide 2 — The Version-Aware Request Pipeline

```text
JSON configuration
    ↓ exact version dispatch
Version-specific closed request type
    ↓ version-specific adapter
CommonRequestIR
    ↓ shared normalization
ExecutionRequest
    ↓
Selected backend
```

- Each version owns its accepted JSON shape, aliases, defaults, and request
  roots.
- Request roots are phase-specific: one-shot, provision, start, exec, stop,
  and deprovision.
- One-shot requests carry policy and process together for one execution.
- State-aware requests establish policy during provision and then drive the
  sandbox through start, exec, stop, and deprovision operations.
- Version-specific adapters translate each exact contract into
  `CommonRequestIR`.
- Shared normalization produces the current `ExecutionRequest` consumed by
  backends.

**Key takeaway:** The contract boundary owns wire-version differences; the
execution path operates on one normalized runtime model.

## Slide 3 — What Developers Must Do

When adding a configuration feature:

1. Decide **which contract first exposes the feature**.
2. Add it to that version's exact Rust contract.
3. Add or update the contract-to-runtime adapter.
4. Register any new request root in `ContractDescriptor`.
5. Add valid and invalid fixtures for every applicable root.
6. Regenerate the schema and TypeScript wire oracle.
7. Update public SDK types, runtime validation, and documentation as
   applicable.

**Development practices**

- Treat schemas in `schemas/stable/` as immutable published artifacts.
- Generate schemas and TypeScript wire oracles from the authoritative Rust
  contracts.
- Add new fields to the current development contract.
- Preserve optional-field presence through adapters.
- Apply shared normalization after exact parsing.
- Apply backend-specific semantic validation in the selected backend.
- Use generated TypeScript wire files as drift oracles.
- Design public SDK types independently around high-level policy intent.

## Slide 4 — The v1 Compatibility Model

**High-level SDK APIs target a major version line.**

- Consumers should be able to upgrade between compatible SDK minor versions
  while existing application code continues to compile and express the same
  intent.
- Consumers adopt newly added minor-version features through optional API
  additions.
- A new major line provides the boundary for intentional source changes.
- Raw configuration documents declare an exact contract version.
- Each SDK release targets the latest minor contract in its major line.
- SDK 1.0 targets `1.0.0`; SDK 1.1 targets `1.1.0`.
- v1 high-level networking uses directional egress, ingress, and host-loopback
  policy.

```text
SDK 1.0 application
    → upgrades to SDK 1.1
    → existing code continues to work
    → new 1.1 fields are available when explicitly adopted
```

**Architecture and direction**

- Exact registered contracts and version-specific adapters exist today.
- Major-line SDK compatibility is the planned v1 SDK behavior.

**Key takeaway:** Exact wire contracts give the native boundary strictness;
major-line SDK APIs give consumers compatibility.

## Slide 5 — The v1 Contract Lineage and Safety Gates

### Contract lineage

- Published `1.0.0` starts from the published v0.9 contract.
- `1.0.0` uses the canonical `processContainer` and `seatbelt` names.
- The v0.10 development lineage becomes development `1.1.0`.
- `1.1.0` carries the features developed in v0.10:
  - abstract `vm` containment;
  - Windows Sandbox one-shot and provision surfaces;
  - Windows Sandbox timeout and daemon-pipe fields;
  - MicroVM;
  - Hyperlight; and
  - the top-level test feature.
- WSLC, IsolationSession, directional networking, and common state-aware
  phases form part of the `1.0.0` baseline.

### CI protects the promise

- Regenerated schemas and TypeScript oracles match committed artifacts.
- Rust fixtures verify each exact Serde contract boundary.
- AJV verifies that the generated schema expresses the same boundary.
- The repository config corpus is validated against the exact schema named by
  each config.
- Schema-version constants are checked across Rust, Node, and .NET.
- Compatibility gates classify contract changes and verify SDK source and
  behavioral compatibility across v1 minor releases.

**Question to ask before opening a PR:**

> Which exact contract owns this field, and what compatibility promise does
> adding it create?
